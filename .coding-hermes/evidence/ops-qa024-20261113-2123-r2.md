## New finding discovered while re-verifying (named, not filed)

The image build at HEAD runs the repo's Go suite inside the Dockerfile (line 102):

```
RUN go test -v -short -timeout 120s $(go list ./... | grep -v …) 2>&1 | tee test-results.txt
```

The pipeline's exit status is `tee`'s, so the step can never fail the build. In this very build,
12+ `--- FAIL` markers appeared (`TestBackupScriptsSyntax` ×4, `TestKubernetesBackupCronJobExists`,
`TestK8sOverlaysExist` dev/staging/prod) and the image was still built and tagged (`up_rc=0`).
The same tests **PASS on the host at the same tree** (`go test ./deployments/backup/ -run
'TestBackupScriptsSyntax|TestKubernetesBackupCronJobExists|TestK8sOverlaysExist' -v` → all PASS,
`ok github.com/wojons/muster/deployments/backup 0.011s`), so the in-build failures are a
build-context path/layout effect — currently invisible because the gate is dead.

Blast radius: repairing the pipe would turn the image build red until the build-context path
failures are fixed, so this is not an ops-lane bounded fix. Named here for the next tick / foreman;
no row filed by this lane.
