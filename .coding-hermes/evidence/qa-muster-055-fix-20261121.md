# QA-MUSTER-055 — TestBinaryExecution_ContextTimeout: deterministic teardown property instead of a 2s wall clock

Date: 2026-11-21
Branch: wt/QA-MUSTER-055 (base 113bd123 = origin/main)
Scope: `cmd/mcp-server/integration_test.go` (test only; no production code changed)
Sibling lanes untouched: harness `~/.hermes/scripts/bunker-qa.sh` (QA-MUSTER-13-R2), `pkg/generator`/`pkg/openapi`/`pkg/mcp` (QA-MUSTER-041).

## 1. Root cause

`TestBinaryExecution_ContextTimeout` started the mcp-server binary under a 500ms
`exec.CommandContext` deadline (stdin held open so the child cannot take a fast EOF
exit), then asserted:

```go
start := time.Now()
err = cmd.Run()
duration := time.Since(start)
...
require.Less(t, duration, 2*time.Second, "Binary should exit within 2 seconds")
```

`duration` is the wall-clock time from `Run()` (start) to `Run()` returning (Wait
completed), i.e. deadline + process-kill + OS reap + pipe drain. The 2s bound is a
hand-picked ceiling on that total for one specific runner class, not a statement about
the code under test. On windows-latest the same correct teardown took 3.5874287s
(evidence: run 44719080001, job 136229845921) and reded `Cross-Platform Tests` — the
assertion measured how loaded/which-platform the runner was, not whether the deadline
stopped the child.

The test also could not distinguish "teardown happened" from "teardown was slow": the
only load-bearing arms were `require.Error` + `ctx.Err() == DeadlineExceeded`, both of
which the 2s ceiling sat on top of as a *timing* proxy.

Linux baseline measured in this worktree (pre-fix file restored from HEAD, go 1.26.11):

```
integration_test.go:267: Binary execution duration: 502.980048ms, wait error: signal: killed
--- PASS: TestBinaryExecution_ContextTimeout (1.27s)
```

502.98ms — passes here, which is exactly why the defect hides on Linux (AC 5). Nothing
about the fix is a Linux-vs-Windows behavior change; it removes the measurement.

## 2. The fix — assert the property, no duration assertion

Replaced the wall-clock ceiling with four deterministic arms:

```go
require.Error(t, err, "the stdio server should be stopped by the context deadline")
require.ErrorIs(t, ctx.Err(), context.DeadlineExceeded,
    "the context deadline must be what terminated the child")
require.NotNil(t, cmd.ProcessState,
    "Run must have returned from Wait, so the child was reaped rather than left running")
require.Error(t, cmd.Process.Signal(os.Kill),
    "the child must already be gone: a live process would accept the signal")
```

`duration` is still logged (`t.Logf`), labelled diagnostic-only, and never asserted.

Why each arm is the property and not a proxy:

- `err != nil` — `Run()` failing means the child was terminated abnormally (an
  `*exec.ExitError`, here `signal: killed`), not a clean exit.
- `ctx.Err() == context.DeadlineExceeded` — attributes the termination to the deadline
  we set, not to an incidental exit (e.g. stdin EOF).
- `cmd.ProcessState != nil` — `Run() == Start() + Wait()`; a non-nil `ProcessState` can
  only exist after `Wait()` returned, i.e. the OS reaped the child. This is the "Wait
  returned" arm AC(2) names. **No zombie / no live process is left behind.**
- `cmd.Process.Signal(os.Kill)` returning an error — a live process accepts `os.Kill`
  and returns nil; a reaped one refuses.

## 3. Why this shape is platform-safe

Measured on this host (go 1.26.11, scratch probe replicating the test's shape):

| scenario | ctx.Err() | Run() err | ProcessState | post-Wait Signal(os.Kill) |
|---|---|---|---|---|
| deadline-killed child (stdin held open) | `context deadline exceeded` | `signal: killed` | non-nil | `os: process already finished` |
| clean-exit child (EOF, no deadline) | nil | nil | non-nil | `os: process already finished` |
| started, not yet waited (live) | — | — | nil | nil (signal accepted) |

Two traps avoided:

1. **`ProcessState.Exited()` is NOT a usable predicate.** On Unix it is
   `syscall.WaitStatus.Exited()` = `WIFEXITED`, which is FALSE for a child terminated
   by a signal — an intermediate edit of this fix used it and the run failed here
   (`Should be true ... the child must be terminated`). Confirmed in
   `$GOROOT/src/os/exec_posix.go:109` (`return p.status.Exited()`) and
   `syscall_linux.go:469`.
2. **The post-Wait signal error differs by platform**, so only "it refused" is asserted,
   not a specific sentinel: Unix returns `os.ErrProcessDone`
   (`os/exec_unix.go:pidSignal` → `statusDone`), Windows returns `syscall.EINVAL`
   because `exec_windows.go:wait()` calls `p.doRelease(statusReleased)`
   (`exec_windows.go:signal` → `case statusReleased: return syscall.EINVAL`). Both are
   non-nil errors; `require.Error` holds on both.

No timing value appears in any assertion, so runner load, Windows process-teardown
latency, and antivirus/CI overhead cannot flip it. The only time constant left is the
500ms context deadline, which bounds *when* the test's own trigger fires (a test input,
not a teardown SLA) and is unchanged from before.

## 4. INT-CI-016 precedent (same defect class, same repo)

`internal/builtin/audit_retention_test.go:213-236`:

```go
// INT-CI-016: this used to compare wall-clock durations
// (largeDur <= 2*smallDur and largeDur < 250ms). That measured how busy
// the runner was, not whether the read is bounded: on macOS CI, 200 rows
// took 115.6us and 10000 rows 131.8us — a 14% difference from pure
// jitter — and failed the run. Boundedness is asserted below on the
// quantity that actually defines it: bytes pulled off the sink.
```

and the replacement bound at `audit_retention_test.go:231-236`:

```go
// One 64KiB tail block is all a single newest row may cost.
const tailBlock = int64(64 * 1024)
assert.LessOrEqual(t, largeBytes, tailBlock,
    "audit log --limit 1 must read at most one tail block: ...")
```

The precedent's accepted shape is: replace wall clock with a quantity intrinsic to the
behavior under test (bytes read via `countingAuditSink`). This fix mirrors it: the
intrinsic quantities are `ctx.Err()`, whether `Wait` completed (`ProcessState`), and
whether the child still accepts a signal.
