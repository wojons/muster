
## Dogfood Findings (2026-09-26) — live peer-API integration: muster → consensus (CONSENSUS-INT-001 angle, run 11)

Verdict: PROMISING-BUT-ROUGH (the CLI data plane is genuinely strong against a foreign live API — full chain proven in minutes; but two of the three non-CLI surfaces cannot reach an authenticated API at all)
Promise: "Point muster at any OpenAPI-described service and use it as CLI, MCP server, and Starlark DSL — no codegen." Reality: CLI leg fully holds against a live harness (consensus, 60-path bearer-auth API): discover (served /openapi.json AND bundled.yaml) → generate (70 commands, zero collisions) → `auth add` bearer → real 201 create / 200 message / 200 list / clean 404 + 401 error paths. MCP leg: initialize + tools/list (70 tools) work, then EVERY authed tools/call 401s — the MCP server has no auth surface at all. DSL leg: HTTP builtins carry no headers, so the authed 3-step workflow is impossible.
Note: dogfood lane does not modify code — DF-036..040 filed to the board for the foreman.

- [P1] DF-036 — openapi-mcp has zero auth mechanism (no flag, no env, no keychain path; pkg/mcp/openapi_integration.go sets Content-Type only; MUSTER_AUTH_TOKEN used by the CLI loader is NOT consulted here). Proven: tools/call createSession/listSessions vs live consensus → upstream "HTTP 401 UNAUTHENTICATED missing API key" every time, while the identical call works from the CLI via `--auth`. Any agent wiring muster's MCP to an authed API is dead at the first authed tool call. Fix + acceptance in board row.
- [P2] DF-037 — Starlark http_get/post/put/delete builtins accept no headers (internal/builtin/dsl.go:98-110); http_post against consensus /api/v1/sessions returns 401 as body text. The workflow shape musterflow needs (create → message → poll) cannot run against a bearer-auth API. Acceptance: optional headers-dict parameter on the builtins + documented authed example.
- [P2] DF-038 — MCP tools/call renders upstream failures as flat isError text ("Error: HTTP 401: {json}") with no distinction between client-side wiring errors (missing credential) and genuine upstream errors; success responses are also dumped as one text blob. The agent-consumer gets no hint that muster dropped the credential. Acceptance: typed/structured error content naming the remedy.
- [P3] DF-039 — `create-session` table output prints the returned session-scoped API key (cs_sk_*) in cleartext; `auth add` masks secrets but the request path does not. Acceptance: mask credential-shaped values in table rendering unless --raw.
- [P2] DF-040 — nothing in docs/ records the "bring your own live API" recipe that CONSENSUS-INT-001 demands: discover URL-or-file → generate --base-url → auth add → per-command --auth/--base-url (or MUSTER_BASE_URL + MUSTER_AUTH_TOKEN). Proven end-to-end in <2 min from a clean HOME; discover handles both the served /openapi.json and the repo's bundled.yaml (85 ops listed). Ship docs/integration-guide.md with the recipe + current MCP/DSL auth caveats.

Install leg: SKIPPED-install-bunker — las-03 (the designated host) tailnet offline 7h (ssh connect timeout to its IP ×1, ssh/tailscale status: "offline, last seen 7h ago"); las-01/04 offline 10h/15h; las-02 reachable but `systemctl is-active bunkerd` = "activating" (crash-loop recovery in progress, matches prior runs) and bunker CLI's registry port 10001 refused. Install surface DID drift since the last proven leg (d9d38a9b bumped kin-openapi 0.148→0.149, sqlite3, seccomp in go.mod/go.sum), so installability at current HEAD is UNPROVEN — next dogfood must re-run the leg when a bunker is healthy.

Measured (perf Step 2b): `hyperfine --warmup 3 --runs 20 'openapi-cli discover <60-path spec>'` → 26.1 ms ± 2.1 ms warm; cold `generate` 27 ms; full authed `list-sessions` round-trip vs live server 106 ms. Nothing a user would notice — no PERF rows filed (5th consecutive run).
