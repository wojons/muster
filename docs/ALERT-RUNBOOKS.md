# Alert Runbooks for Muster

## Overview

This document provides operational runbooks for responding to alerts generated by Muster's monitoring system. Each alert has specific remediation steps and escalation procedures.

Every expression below is written against the metric families the daemon actually serves (`internal/monitoring/muster.go`); `prometheus/rules/alerts.yml` carries the same expressions, so a section here and a rule there always pair. Metric names, label sets, the served port/path and the seed series are documented in `docs/guides/daemon-operations.md`.

## Alert Severity Levels

| Severity | Response Time | Notification Channels | SLA |
|----------|---------------|----------------------|-----|
| **Critical** | Immediate | PagerDuty + Slack + Email | 5 min |
| **Warning** | 15 minutes | Slack + Email | 15 min |
| **Info** | 1 hour | Email only | 1 hour |

## Alert: HighErrorRate

**Severity:** Critical  
**Expression:** `sum(rate(muster_daemon_proxy_requests_total{status_class="5xx"}[5m])) / sum(rate(muster_daemon_proxy_requests_total[5m])) > 0.05`  
**Duration:** Fires after 5 minutes of elevated errors

### Symptoms
- 5xx share of proxied daemon requests exceeds 5%
- Affects every path the daemon proxies (the `endpoint` label carries the sanitized path)
- May indicate upstream degradation

### Diagnostic Steps

1. **Check service health**
   ```bash
   curl --unix-socket /tmp/openapi-cli.sock -s http://localhost/health
   ```

2. **View recent errors**
   ```bash
   journalctl -u muster-daemon --since "15 minutes ago" | grep ERROR
   ```

3. **Check error distribution**
   ```bash
   # 5xx split by endpoint (add by (endpoint) to see which route is failing)
   curl -s 'http://localhost:9090/api/v1/query?query=sum(rate(muster_daemon_proxy_requests_total{status_class="5xx"}[5m]))by(endpoint)'
   ```

### Remediation Steps

1. **Immediate (0-5 min)**
   - Check if service is responding: `curl http://localhost:8080/ping`
   - Review recent deployments: `git log --oneline -10`
   - Check resource usage: `htop` or `docker stats`

2. **Short-term (5-15 min)**
   - Restart service if necessary: `sudo systemctl restart muster-daemon`
   - Check database connections: `netstat -an | grep :5432`
   - Review logs for stack traces: `grep -A 20 "panic" /var/log/muster/app.log`

3. **Long-term (15+ min)**
   - Analyze error patterns in logs
   - Check for upstream dependency failures
   - Review rate limiting configuration

### Escalation

If error rate persists after 15 minutes:
1. **Escalate to:** Engineering lead
2. **Create incident:** #incidents Slack channel
3. **Notify:** On-call engineer via PagerDuty

## Alert: HighLatency

**Severity:** Warning  
**Expression:** `histogram_quantile(0.95, sum(rate(muster_daemon_proxy_duration_seconds_bucket[5m])) by (le)) > 0.5`  
**Duration:** Fires after 10 minutes

### Symptoms
- 95th percentile proxied-request latency exceeds 500ms
- May indicate resource contention or upstream slowness

### Diagnostic Steps

1. **Check latency distribution**
   ```bash
   curl -s 'http://localhost:9090/api/v1/query?query=histogram_quantile(0.95,sum(rate(muster_daemon_proxy_duration_seconds_bucket[5m]))by(le))'
   ```

2. **Identify slow endpoints**
   ```bash
   # Check per-endpoint latency
   grep "duration" /var/log/muster/access.log | sort -k4 -rn | head -20
   ```

3. **Check resource utilization**
   ```bash
   # CPU and memory
   top -b -n1 | head -20
   free -h
   ```

### Remediation Steps

1. **Immediate (0-15 min)**
   - Enable request sampling for profiling
   - Check for blocking operations in logs
   - Check the daemon's own latency series: `curl -fsS http://127.0.0.1:9110/metrics | grep muster_daemon_proxy_duration_seconds`

2. **Short-term (15-30 min)**
   - Scale service horizontally if needed
   - Review database query performance
   - Check external API dependencies

3. **Long-term (30+ min)**
   - Optimize slow code paths
   - Reduce upstream round trips
   - Consider circuit breaker for slow dependencies

### Escalation

If latency > 1s for > 30 minutes:
1. **Escalate to:** Engineering lead
2. **Create ticket:** High priority in ticketing system

## Alert: LowDiskSpace

**Severity:** Warning  
**Expression:** `node_filesystem_avail_bytes / node_filesystem_size_bytes < 0.1`  
**Duration:** Fires after 5 minutes

### Symptoms
- Available disk space below 10%
- Risk of service failure due to inability to write logs/cache

### Diagnostic Steps

1. **Check disk usage**
   ```bash
   df -h
   du -sh /var/log/* | sort -hr | head -20
   ```

2. **Check log rotation**
   ```bash
   ls -la /var/log/muster/
   logrotate --debug /etc/logrotate.d/muster
   ```

3. **Check cache size**
   ```bash
   du -sh /var/cache/muster/
   find /var/cache/muster -type f -mtime +7 -exec ls -lh {} \;
   ```

### Remediation Steps

1. **Immediate (0-15 min)**
   ```bash
   # Clean old logs
   find /var/log/muster -name "*.log.*" -mtime +7 -delete
   
   # Clean old cache
   find /var/cache/muster -type f -mtime +3 -delete
   
   # Force log rotation
   logrotate -f /etc/logrotate.d/muster
   ```

2. **Short-term (15-30 min)**
   - Review log retention policies
   - Adjust cache TTL settings
   - Add disk space if consistently full

3. **Long-term**
   - Implement automated cleanup jobs
   - Set up log aggregation (ELK/Loki)
   - Monitor disk usage trends

### Escalation

If disk space < 5%:
1. **Escalate to:** Infrastructure team
2. **Urgent:** Risk of service crash

## Alert: HighMemoryUsage

**Severity:** Warning  
**Expression:** `(node_memory_MemTotal_bytes - node_memory_MemAvailable_bytes) / node_memory_MemTotal_bytes > 0.85`  
**Duration:** Fires after 5 minutes

### Symptoms
- Memory usage exceeds 85%
- Risk of OOM killer terminating processes

### Diagnostic Steps

1. **Check memory usage**
   ```bash
   free -h
   ps aux --sort=-%mem | head -20
   ```

2. **Check for memory leaks**
   ```bash
   # Monitor memory over time
   watch -n 5 'ps -o pid,rss,comm -p $(pgrep muster)'
   ```

3. **Check swap usage**
   ```bash
   swapon -s
   vmstat 1 10
   ```

### Remediation Steps

1. **Immediate (0-15 min)**
   ```bash
   # Check for runaway processes
   ps aux --sort=-%mem | head -10
   
   # Restart service if memory leak suspected
   sudo systemctl restart muster-daemon
   ```

2. **Short-term (15-30 min)**
   - Analyze heap dumps if available
   - Review recent changes in memory-intensive code
   - Check cache size limits

3. **Long-term**
   - Profile application memory usage
   - Implement memory limits in container configs
   - Add horizontal scaling

### Escalation

If memory > 95%:
1. **Escalate to:** Engineering team
2. **Risk:** Service instability, OOM kills

## Alert: HighCPUUsage

**Severity:** Info  
**Expression:** `100 - (avg by (instance) (irate(node_cpu_seconds_total{mode="idle"}[5m])) * 100) > 80`  
**Duration:** Fires after 10 minutes

### Symptoms
- Host CPU above 80% for 10 minutes
- Proxied request latency usually rises with it (`muster_daemon_proxy_duration_seconds`)

### Diagnostic Steps

1. **Find the consumer**
   ```bash
   top -b -n1 | head -20
   ps aux --sort=-%cpu | head -10
   ```

2. **Check whether the daemon itself is the cause**
   ```bash
   curl -fsS http://127.0.0.1:9110/metrics | grep -E '^muster_(daemon_proxy_duration_seconds_count|mcp_active_sessions)'
   ```

### Remediation Steps

1. **Immediate (0-15 min)**
   - Identify the top process; throttle or stop it if it is not the daemon
   - Check for a runaway test/build process before blaming the service

2. **Short-term (15-30 min)**
   - Restart the unit if CPU stays pinned with no traffic
   - Review recent traffic shape and upstream latency

3. **Long-term**
   - Add CPU limits in the deployment
   - Correlate CPU with request rate before tuning thresholds

### Escalation

If CPU > 95% for > 30 minutes:
1. **Escalate to:** Infrastructure team
2. **Risk:** Latency SLO breach

## Alert: MusterDaemonDown

**Severity:** Critical  
**Expression:** `muster_daemon_up == 0`  
**Duration:** Fires after 1 minute

### Symptoms
- The daemon reports itself as not serving for more than a minute
- `muster_daemon_up` is 0 from process start until the Unix socket answers, and is set back to 0 on the shutdown path, so a flap means the daemon restarted or is stuck in startup

### Diagnostic Steps

1. **Check the unit**
   ```bash
   sudo systemctl status muster-daemon
   ```

2. **Check whether the socket answers**
   ```bash
   curl --unix-socket /run/muster/daemon.sock -s http://localhost/health
   ```

3. **Confirm which build the scrape target is**
   ```bash
   curl -fsS http://127.0.0.1:9110/metrics | grep '^muster_build_info'
   ```

4. **Read the startup/shutdown log**
   ```bash
   journalctl -u muster-daemon -n 100 --no-pager
   ```

### Remediation Steps

1. **Immediate (0-5 min)**
   - Start or restart the unit: `sudo systemctl restart muster-daemon`
   - If the unit is active but the alert persists, the scrape target is a different
     process: compare `muster_build_info{commit=...}` against the deployed binary
   - Confirm the metrics listener came up: the startup log prints
     `Metrics: http://127.0.0.1:9110/metrics`, and a busy port prints
     `[WARN] metrics listener not started` instead

2. **Short-term (5-15 min)**
   - Review the log for the exit reason (panic, OOM kill, `daemon stopped`)
   - Check disk and memory pressure on the host
   - Verify the socket path in the unit's `ExecStart` matches the one clients use

3. **Long-term**
   - The shipped `systemd/muster-daemon.service` has no `Restart=` policy; adding
     `Restart=on-failure` makes a crash self-healing
   - Probe the socket path directly in addition to `muster_daemon_up`

### Escalation

If the daemon is down for > 5 minutes:
1. **Escalate to:** On-call engineer
2. **Escalate to:** Infrastructure team (if the host itself is unhealthy)

## Alert: ServiceDown

**Severity:** Critical  
**Expression:** `up == 0`  
**Duration:** Fires after 1 minute

### Symptoms
- Service not responding to health checks
- Complete service outage

### Diagnostic Steps

1. **Check service status**
   ```bash
   sudo systemctl status muster-daemon
   sudo systemctl status muster-mcp
   ```

2. **Check process status**
   ```bash
   ps aux | grep muster
   netstat -tlnp | grep :8080
   ```

3. **Check recent logs**
   ```bash
   journalctl -u muster-daemon -n 100 --no-pager
   ```

### Remediation Steps

1. **Immediate (0-2 min)**
   ```bash
   # Try to start service
   sudo systemctl start muster-daemon
   
   # Check if port is in use
   sudo lsof -i :8080
   ```

2. **Short-term (2-10 min)**
   - Review panic/crash logs
   - Check for dependency failures
   - Verify configuration files

3. **Long-term (10+ min)**
   - Analyze root cause from logs
   - Fix underlying issue
   - Update monitoring thresholds if false positive

### Escalation

This is a **critical alert** - immediate escalation required:
1. **Page on-call engineer immediately**
2. **Create P1 incident**
3. **Notify:** Team lead and stakeholders
4. **War room:** #incidents-war-room

## Alert: HighMCPToolLatency

**Severity:** Warning  
**Expression:** `histogram_quantile(0.95, sum(rate(muster_mcp_tool_duration_seconds_bucket[5m])) by (le)) > 1.0`  
**Duration:** Fires after 5 minutes

### Symptoms
- MCP (Model Context Protocol) tool calls taking > 1 second
- May affect AI assistant response times
- These families are published by the stdio `mcp-server` through a node_exporter
  textfile (`/var/lib/node_exporter/textfile/muster_mcp.prom`), not by the daemon's
  loopback listener — a missing textfile makes the series vanish rather than stay flat

### Diagnostic Steps

1. **Check the published textfile**
   ```bash
   tail -30 /var/lib/node_exporter/textfile/muster_mcp.prom
   ```

2. **Review MCP logs**
   ```bash
   grep "mcp" /var/log/muster/app.log | tail -100
   ```

3. **Break the latency down by tool**
   ```bash
   curl -s 'http://localhost:9090/api/v1/query?query=histogram_quantile(0.95,sum(rate(muster_mcp_tool_duration_seconds_bucket[5m]))by(tool,le))'
   ```

4. **Check WASM execution times**
   ```bash
   # If WASM modules are slow
   grep "wasm" /var/log/muster/app.log | grep "duration"
   ```

### Remediation Steps

1. **Immediate (0-15 min)**
   - Check WASM module performance
   - Verify cache hit ratios
   - Restart MCP service if stuck

2. **Short-term (15-30 min)**
   - Profile MCP handler code
   - Check for blocking operations
   - Review concurrent request handling

3. **Long-term**
   - Optimize WASM module loading
   - Add caching for MCP responses
   - Consider request queuing

### Escalation

If MCP latency > 5s:
1. **Escalate to:** MCP team lead
2. **Impact:** AI assistant performance degraded

## Alert: MusterAuditEventsDropped

**Severity:** Warning  
**Expression:** `increase(muster_audit_events_dropped_total[5m]) > 0`  
**Duration:** Fires after 2 minutes

### Symptoms
- The audit sink rejected or lost events: `reason="buffer_full"` (the buffer filled faster than it drains) or `reason="write_error"` (the record-of-truth write failed)
- The audit trail is lossy — a compliance concern, not just a performance one

### Diagnostic Steps

1. **See which reason is firing and how fast**
   ```bash
   curl -s 'http://localhost:9090/api/v1/query?query=increase(muster_audit_events_dropped_total[5m])'
   ```

2. **Check buffer pressure**
   ```bash
   curl -fsS http://127.0.0.1:9110/metrics | grep muster_audit_buffer_utilization_ratio
   ```

3. **Check the audit log destination**
   ```bash
   ls -l "$MUSTER_AUDIT_LOG"
   df -h "$(dirname "$MUSTER_AUDIT_LOG")"
   ```

### Remediation Steps

1. **Immediate (0-15 min)**
   - If `write_error`: fix the destination (permissions, free space, path)
   - If `buffer_full`: reduce audit volume or raise the buffer size, then restart the daemon
   - Confirm `muster_audit_events_written_total` is climbing again

2. **Short-term (15-30 min)**
   - Move the audit log to a filesystem with headroom
   - Check for a single noisy event type flooding the buffer

3. **Long-term**
   - Ship audit events to a durable sink off-box
   - Alert on `muster_audit_buffer_utilization_ratio` before drops start

### Escalation

If events are still being dropped after 30 minutes:
1. **Escalate to:** Compliance owner (the audit trail is incomplete)
2. **Record:** the window and the dropped count for the incident report

## Quick Reference

### Useful Commands

```bash
# Check all service statuses
systemctl status muster-*

# View logs
journalctl -u muster-daemon -f

# Health check (Unix socket)
curl --unix-socket /run/muster/daemon.sock -s http://localhost/health

# Metrics (loopback listener; the socket's /metrics path is JSON, not Prometheus)
curl -fsS http://127.0.0.1:9110/metrics | grep -E '^muster_'

# Restart all services
systemctl restart muster-daemon muster-mcp
```

### Alert Silence

To silence an alert during maintenance:

```bash
# Via AlertManager API
curl -X POST http://alertmanager:9093/api/v1/silences \
  -H "Content-Type: application/json" \
  -d '{
    "matchers": [
      {"name": "alertname", "value": "ServiceDown"},
      {"name": "service", "value": "api"}
    ],
    "startsAt": "'$(date -u +%Y-%m-%dT%H:%M:%SZ)'",
    "endsAt": "'$(date -u -d '+1 hour' +%Y-%m-%dT%H:%M:%SZ)'",
    "createdBy": "ops-team",
    "comment": "Scheduled maintenance"
  }'
```
