# Alert Runbooks for Muster

## Overview

This document provides operational runbooks for responding to alerts generated by Muster's monitoring system. Each alert has specific remediation steps and escalation procedures.

## Alert Severity Levels

| Severity | Response Time | Notification Channels | SLA |
|----------|---------------|----------------------|-----|
| **Critical** | Immediate | PagerDuty + Slack + Email | 5 min |
| **Warning** | 15 minutes | Slack + Email | 15 min |
| **Info** | 1 hour | Email only | 1 hour |

## Alert: HighErrorRate

**Severity:** Critical  
**Expression:** `rate(http_requests_total{status_code=~"5.."}[5m]) / rate(http_requests_total[5m]) > 0.05`  
**Duration:** Fires after 5 minutes of elevated errors

### Symptoms
- HTTP 5xx error rate exceeds 5% of total requests
- Affects API endpoints
- May indicate service degradation

### Diagnostic Steps

1. **Check service health**
   ```bash
   curl -s http://localhost:8080/health
   ```

2. **View recent errors**
   ```bash
   journalctl -u muster-daemon --since "15 minutes ago" | grep ERROR
   ```

3. **Check error distribution**
   ```bash
   # Look for specific error codes
   curl -s http://localhost:9090/api/v1/query?query=sum(rate(http_requests_total{status_code=~"5.."}[5m]))by(status_code)
   ```

### Remediation Steps

1. **Immediate (0-5 min)**
   - Check if service is responding: `curl http://localhost:8080/ping`
   - Review recent deployments: `git log --oneline -10`
   - Check resource usage: `htop` or `docker stats`

2. **Short-term (5-15 min)**
   - Restart service if necessary: `sudo systemctl restart muster-daemon`
   - Check database connections: `netstat -an | grep :5432`
   - Review logs for stack traces: `grep -A 20 "panic" /var/log/muster/app.log`

3. **Long-term (15+ min)**
   - Analyze error patterns in logs
   - Check for upstream dependency failures
   - Review rate limiting configuration

### Escalation

If error rate persists after 15 minutes:
1. **Escalate to:** Engineering lead
2. **Create incident:** #incidents Slack channel
3. **Notify:** On-call engineer via PagerDuty

## Alert: HighLatency

**Severity:** Warning  
**Expression:** `histogram_quantile(0.95, rate(request_duration_seconds_bucket[5m])) > 0.5`  
**Duration:** Fires after 10 minutes

### Symptoms
- 95th percentile latency exceeds 500ms
- May indicate resource contention or upstream slowness

### Diagnostic Steps

1. **Check latency distribution**
   ```bash
   curl -s http://localhost:9090/api/v1/query?query=histogram_quantile(0.95,sum(rate(request_duration_seconds_bucket[5m]))by(le))
   ```

2. **Identify slow endpoints**
   ```bash
   # Check per-endpoint latency
   grep "duration" /var/log/muster/access.log | sort -k4 -rn | head -20
   ```

3. **Check resource utilization**
   ```bash
   # CPU and memory
   top -b -n1 | head -20
   free -h
   ```

### Remediation Steps

1. **Immediate (0-15 min)**
   - Enable request sampling for profiling
   - Check for blocking operations in logs
   - Verify cache hit ratio: `sum(rate(cache_hits_total[5m])) / sum(rate(cache_hits_total[5m]) + rate(cache_misses_total[5m]))`

2. **Short-term (15-30 min)**
   - Scale service horizontally if needed
   - Review database query performance
   - Check external API dependencies

3. **Long-term (30+ min)**
   - Optimize slow code paths
   - Add caching for expensive operations
   - Consider circuit breaker for slow dependencies

### Escalation

If latency > 1s for > 30 minutes:
1. **Escalate to:** Engineering lead
2. **Create ticket:** High priority in ticketing system

## Alert: LowDiskSpace

**Severity:** Warning  
**Expression:** `node_filesystem_avail_bytes / node_filesystem_size_bytes < 0.1`  
**Duration:** Fires after 5 minutes

### Symptoms
- Available disk space below 10%
- Risk of service failure due to inability to write logs/cache

### Diagnostic Steps

1. **Check disk usage**
   ```bash
   df -h
   du -sh /var/log/* | sort -hr | head -20
   ```

2. **Check log rotation**
   ```bash
   ls -la /var/log/muster/
   logrotate --debug /etc/logrotate.d/muster
   ```

3. **Check cache size**
   ```bash
   du -sh /var/cache/muster/
   find /var/cache/muster -type f -mtime +7 -exec ls -lh {} \;
   ```

### Remediation Steps

1. **Immediate (0-15 min)**
   ```bash
   # Clean old logs
   find /var/log/muster -name "*.log.*" -mtime +7 -delete
   
   # Clean old cache
   find /var/cache/muster -type f -mtime +3 -delete
   
   # Force log rotation
   logrotate -f /etc/logrotate.d/muster
   ```

2. **Short-term (15-30 min)**
   - Review log retention policies
   - Adjust cache TTL settings
   - Add disk space if consistently full

3. **Long-term**
   - Implement automated cleanup jobs
   - Set up log aggregation (ELK/Loki)
   - Monitor disk usage trends

### Escalation

If disk space < 5%:
1. **Escalate to:** Infrastructure team
2. **Urgent:** Risk of service crash

## Alert: HighMemoryUsage

**Severity:** Warning  
**Expression:** `(node_memory_MemTotal_bytes - node_memory_MemAvailable_bytes) / node_memory_MemTotal_bytes > 0.85`  
**Duration:** Fires after 5 minutes

### Symptoms
- Memory usage exceeds 85%
- Risk of OOM killer terminating processes

### Diagnostic Steps

1. **Check memory usage**
   ```bash
   free -h
   ps aux --sort=-%mem | head -20
   ```

2. **Check for memory leaks**
   ```bash
   # Monitor memory over time
   watch -n 5 'ps -o pid,rss,comm -p $(pgrep muster)'
   ```

3. **Check swap usage**
   ```bash
   swapon -s
   vmstat 1 10
   ```

### Remediation Steps

1. **Immediate (0-15 min)**
   ```bash
   # Check for runaway processes
   ps aux --sort=-%mem | head -10
   
   # Restart service if memory leak suspected
   sudo systemctl restart muster-daemon
   ```

2. **Short-term (15-30 min)**
   - Analyze heap dumps if available
   - Review recent changes in memory-intensive code
   - Check cache size limits

3. **Long-term**
   - Profile application memory usage
   - Implement memory limits in container configs
   - Add horizontal scaling

### Escalation

If memory > 95%:
1. **Escalate to:** Engineering team
2. **Risk:** Service instability, OOM kills

## Alert: DatabaseConnectionFailures

**Severity:** Critical  
**Expression:** `increase(db_connection_errors_total[5m]) > 10`  
**Duration:** Fires after 2 minutes

### Symptoms
- Database connection errors increasing
- May cause cascading failures across services

### Diagnostic Steps

1. **Check database connectivity**
   ```bash
   psql -h $DB_HOST -U $DB_USER -c "SELECT 1"
   ```

2. **Check connection pool status**
   ```bash
   # If using pg_stat_activity
   psql -c "SELECT count(*) FROM pg_stat_activity WHERE state = 'active'"
   ```

3. **Check network connectivity**
   ```bash
   telnet $DB_HOST $DB_PORT
   netstat -an | grep :5432
   ```

### Remediation Steps

1. **Immediate (0-5 min)**
   - Verify database is reachable
   - Check connection pool exhaustion
   - Review recent connection error logs

2. **Short-term (5-15 min)**
   - Restart application to reset connection pool
   - Check database server status
   - Verify firewall rules

3. **Long-term**
   - Implement connection pool monitoring
   - Add circuit breaker for DB calls
   - Review retry logic

### Escalation

If connections fail for > 5 minutes:
1. **Escalate to:** DBA team
2. **Escalate to:** Infrastructure team (if network issue)

## Alert: ServiceDown

**Severity:** Critical  
**Expression:** `up == 0`  
**Duration:** Fires after 1 minute

### Symptoms
- Service not responding to health checks
- Complete service outage

### Diagnostic Steps

1. **Check service status**
   ```bash
   sudo systemctl status muster-daemon
   sudo systemctl status muster-mcp
   ```

2. **Check process status**
   ```bash
   ps aux | grep muster
   netstat -tlnp | grep :8080
   ```

3. **Check recent logs**
   ```bash
   journalctl -u muster-daemon -n 100 --no-pager
   ```

### Remediation Steps

1. **Immediate (0-2 min)**
   ```bash
   # Try to start service
   sudo systemctl start muster-daemon
   
   # Check if port is in use
   sudo lsof -i :8080
   ```

2. **Short-term (2-10 min)**
   - Review panic/crash logs
   - Check for dependency failures
   - Verify configuration files

3. **Long-term (10+ min)**
   - Analyze root cause from logs
   - Fix underlying issue
   - Update monitoring thresholds if false positive

### Escalation

This is a **critical alert** - immediate escalation required:
1. **Page on-call engineer immediately**
2. **Create P1 incident**
3. **Notify:** Team lead and stakeholders
4. **War room:** #incidents-war-room

## Alert: HighMCPRequestLatency

**Severity:** Warning  
**Expression:** `histogram_quantile(0.95, rate(mcp_request_duration_seconds_bucket[5m])) > 1.0`  
**Duration:** Fires after 5 minutes

### Symptoms
- MCP (Model Context Protocol) requests taking > 1 second
- May affect AI assistant response times

### Diagnostic Steps

1. **Check MCP endpoint latency**
   ```bash
   curl -w "@curl-format.txt" -o /dev/null -s http://localhost:8080/mcp/health
   ```

2. **Review MCP logs**
   ```bash
   grep "mcp" /var/log/muster/app.log | tail -100
   ```

3. **Check WASM execution times**
   ```bash
   # If WASM modules are slow
   grep "wasm" /var/log/muster/app.log | grep "duration"
   ```

### Remediation Steps

1. **Immediate (0-15 min)**
   - Check WASM module performance
   - Verify cache hit ratios
   - Restart MCP service if stuck

2. **Short-term (15-30 min)**
   - Profile MCP handler code
   - Check for blocking operations
   - Review concurrent request handling

3. **Long-term**
   - Optimize WASM module loading
   - Add caching for MCP responses
   - Consider request queuing

### Escalation

If MCP latency > 5s:
1. **Escalate to:** MCP team lead
2. **Impact:** AI assistant performance degraded

## Alert: LowCacheHitRatio

**Severity:** Warning  
**Expression:** `sum(rate(cache_hits_total[5m])) / sum(rate(cache_hits_total[5m]) + rate(cache_misses_total[5m])) < 0.5`  
**Duration:** Fires after 10 minutes

### Symptoms
- Cache hit ratio below 50%
- Increased database load
- Higher latency

### Diagnostic Steps

1. **Check cache statistics**
   ```bash
   curl -s http://localhost:8080/metrics | grep cache
   ```

2. **Check cache size**
   ```bash
   # For Redis
   redis-cli INFO memory
   redis-cli DBSIZE
   ```

3. **Review cache configuration**
   ```bash
   cat /etc/muster/cache.conf | grep -E "(ttl|size|max)"
   ```

### Remediation Steps

1. **Immediate (0-15 min)**
   - Check if cache is populated
   - Warm cache if necessary
   - Verify cache TTL settings

2. **Short-term (15-30 min)**
   - Analyze access patterns
   - Adjust cache key strategy
   - Increase cache size if needed

3. **Long-term**
   - Implement cache warming jobs
   - Review eviction policies
   - Add multi-tier caching

### Escalation

If hit ratio < 30%:
1. **Escalate to:** Performance team
2. **Risk:** Database overload

# Health check
curl http://localhost:8080/health

# Metrics
curl http://localhost:8080/metrics

### Alert Silence

To silence an alert during maintenance:

```bash
# Via AlertManager API
curl -X POST http://alertmanager:9093/api/v1/silences \
  -H "Content-Type: application/json" \
  -d '{
    "matchers": [
      {"name": "alertname", "value": "ServiceDown"},
      {"name": "service", "value": "api"}
    ],
    "startsAt": "'$(date -u +%Y-%m-%dT%H:%M:%SZ)'",
    "endsAt": "'$(date -u -d '+1 hour' +%Y-%m-%dT%H:%M:%SZ)'",
    "createdBy": "ops-team",
    "comment": "Scheduled maintenance"
  }'
```
